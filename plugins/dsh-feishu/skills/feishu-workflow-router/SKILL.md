# 飞书工作流路由（运行时优先）

把本机安装的官方 `lark-cli` 及其内嵌的 `lark-*` 技能当作唯一事实来源。本插件只提供安全路由与判断顺序：不内置飞书 API 封装、不保存任何凭证、不假设记忆里的命令仍然存在。

## 路由顺序

业务调用前严格按顺序执行：

1. **解析目标与意图**：识别资源链接/标识（docx token、base app token、wiki node、chat id、日历 id 等）、要执行的操作、影响的记录或收件人、缺失的必填业务输入；把操作归类为 `read`、`normal-write`、`high-risk-write`。
2. **确认 CLI 可用**：运行 `lark-cli --version`。若缺失或失败，停止业务路由，改用 `feishu-setup`；不要猜命令。
3. **发现能力**：运行 `lark-cli skills list`，以当前输出为能力清单。
4. **读取共享规则**：运行 `lark-cli skills read lark-shared`，再按需读取所选技能。
5. **选择领域**：用 [domain-routing.md](references/domain-routing.md) 匹配当前列出的 `lark-*` 技能，然后 `lark-cli skills read <skill>` 读取该技能，并按它要求读取全部 references。
6. **只在必要时查帮助**：仅当参数、flag 或可用性不确定时查看 `lark-cli <domain> --help`；仅当运行时文档描述了相关 schema 时才用 `lark-cli schema`。不要凭记忆推断命令、端点、字段或 flag。
7. **确定 profile 与身份**：先 `lark-cli profile list`，再用运行时文档给出的状态/身份命令核验当前 profile 的实际身份（通常 `lark-cli whoami`）。记录所选 profile 与脱敏后的身份证据。
8. **刻意选择身份**：需要体现某个人授权、个人访问、所有权或用户级分享时用 **user** 身份；只有操作确实归属应用且目标已分享给该应用时才用 **bot/app** 身份。不要默认强制某一种。无法确认 profile 或实际身份时停下澄清。
9. **写入先预演**：受支持的写操作先加 `--dry-run` 跑一遍，检查目标数量、字段、收件人与变更摘要。运行时没有 dry-run 不等于可以自行发明一个；按所选技能文档给出的预览/确认机制执行，并说明该限制。
10. **高风险写操作必须显式确认**：展示已验证的目标、所选 profile/身份、dry-run 证据与影响后，向用户请求确认。`high-risk-write` 包括删除、批量更新（含 Base 200 条场景）、大范围/外部消息、不可逆的权限或审批变更，以及所选技能/帮助标注需要确认的写操作。普通写操作也要保留上游的确认要求。
11. **执行并核验**：确认后只执行运行时验证过的命令，按所选技能文档的方法回读/核验返回对象。

## 命令选择与失败分类

优先使用当前技能支持的快捷命令，其次它的类型化 API 命令；只有运行时文档提供了原始 API 逃生口且请求确实需要时才使用。静态校验阶段绝不认证、不创建配置、不调用远端 API。

区分并分别报告：CLI/命令不可用、profile 或登录无效、scope 不足、资源未分享、用户输入无效、远端 API 失败。不要为了把一类问题变成另一类而重试、扩权、换 profile 或换身份。

## 完成报告

不要只报“成功”。必须说明：目标、请求的操作、所选 profile 与实际 user/bot 身份、命令与结果证据（含返回 id）、核验结果、部分失败项、遗留限制。若未执行，说明原因并列出缺失的输入、运行时能力、确认或授权。

## 与 Codex 版的差异

- 本技能在 Harness 目录里是**模型可调用**的（Codex 版设为显式调用）。没有这一点，Harness 的模型侧路由就不存在。
- 两个构建共享同一套安全顺序与失败分类；业务命令始终来自当前 `lark-cli`，而不是本文件。
